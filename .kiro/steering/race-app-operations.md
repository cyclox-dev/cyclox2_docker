# 計測アプリ（Cyclox2 race app）の運用上の注意

## 対象

大会ごとに配布する計測アプリ（`<大会フォルダ>/app/`、`Cyclox2.jar` とローカルの
`cyclox2_main_data.sqlite`）で、選手・カテゴリー所属・大会情報をサーバーと同期する作業。
アプリ側の不具合は当面修正しない方針のため（2026-10-06、ユーザー判断）、以下の運用で回避する。
問い合わせ調査で同種のエラーを見たときの切り分けにも使う。

## 押さえるべき仕組み

1. **起動中にフォルダを移動すると、ローカルDBが読み取り専用になる。** SQLiteは開いたときの
   パスにファイルが無くなると書き込みを拒否する（`SQLITE_READONLY_DBMOVED`）。読み込み、
   CSVの書き出し、サーバーへの送信は動き続けるため、異常に気づきにくい。ログに出るパスは
   起動時のパスのまま（実際のファイルは移動先に書かれる）。
2. **アップロードは「送信 → ローカルに送信済みの印を付ける」の2段階。** 印付けに失敗しても
   サーバー側の登録は残る。未送信のまま残った行は、次回のアップロードで**再送されてサーバーに
   重複登録される**。サーバーは同一カテゴリーの重複を拒否しない（`duplicate_category` 警告が
   ログに出るだけ）。
3. **同期の最終更新日時は、ローカル保存の成否に関係なく進む。** `app/props/vars.txt` の
   `MEET_LAST_UPDATE_DATE` / `RACER_LAST_UPDATE_DATE` / `CAT_RACER_LAST_UPDATE_DATE` が
   進むと、保存に失敗したデータは次回の差分同期で取り直されない。
4. **ローカルの未送信行とサーバーから取得した行は突き合わされない。** 大会データのコピーが
   複数あり、別のコピーが先にアップロードすると、こちらのコピーには「未送信の行」と
   「サーバーから取得した同じ内容の行」が並ぶ。こちらからアップロードすると重複になる。

## 運用ルール

- **アプリ起動中に大会フォルダを移動・リネームしない。** 移動するときはアプリを終了してから。
  クラウド同期フォルダ（iCloudの「書類」など）に置いたまま運用しない。
- **大会データのコピー（zip配布など）を渡したら、アップロードする側を1つに決める。**
  受け取った側が選手登録やエントリーをアップロードする場合、渡した側の元データでは
  アップロードしない（使うなら、受け取った側のデータで置き換える）。
- **アップロードでエラーが出たら、再試行しない。** 再試行のたびにサーバーへ同じ行が追加される。
  先に下の確認手順で原因を確かめる。

## エラー時の確認手順

1. `app/log.txt` で `ERROR` 行の理由を見る。`SQLITE_READONLY_DBMOVED` ならフォルダ移動が原因。
   アプリを再起動すれば書き込みは戻るが、**再起動後すぐにアップロードしない**。
2. サーバー側で重複を確認する（サーバーログの `duplicate_category` 警告、または
   `category_racers` を選手コードとカテゴリーで集計）。
3. ローカルの未送信行（`category_racers.id_on_svr IS NULL`）が、サーバーから取得済みの行
   （`id_on_svr` あり）と同じ内容で並んでいないかを確認する。
4. 是正する。手順は下記。是正の内容は、そのタスクの `agreement-log.md` に記録する。

## 是正の手順

- **サーバーの重複行は論理削除する**（`deleted = 1`、`deleted_date` と `modified` を現在時刻に）。
  `modified` を更新すると、差分同期（`updated_category_racers` は削除済みも返す）でアプリにも
  削除が届く。最初に登録された1行は残す。本番で流す前にローカルのダンプでリハーサルする。
- **ローカルの未送信行は、アプリを終了してから削除する**（sqliteを丸ごとバックアップしてから）。
  起動中に書き換えると、アプリが保持している内容で上書きされるおそれがある。
- **進みすぎた同期日時は、アプリを終了してから `vars.txt` で元の値に戻す。** 元の値は、
  失敗前のコピーの `vars.txt` か、サーバーログの `/api/updated_meet_codes/<日時>.json` などの
  リクエストから分かる（アプリは保存値の10分前を送る）。差分同期は取り直すだけなので、
  古めに戻しても害はない。
- 是正後はアプリを起動して、**ダウンロード → アップロード**の順に実行する。アップロードで
  「アップロードするものなし」と出れば完了。

## 補足

- 事例: CXK-267-003（2026-10-06）。経緯と実施したSQLは
  `.kiro/specs/cxk267003-c4-duplicate-2026-10/` を参照。
- アプリを修正する場合の候補は次のとおり（現時点では実施しない）。
  - 送信前にDBへ書き込めるかを確認する。
  - 保存に失敗したら同期日時を進めない。
  - サーバー側で同一カテゴリーの重複登録を拒否する。
