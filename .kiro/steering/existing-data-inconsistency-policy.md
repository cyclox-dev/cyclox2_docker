# 既存データ不整合への向き合い方（プロジェクト全体の既定方針）

[Purpose: 「既存の不整合データに介入しない」という要件が、しばしば「不整合データがあれば
関連する新規処理も一律に見送る」という過剰に保守的な実装に倒れがちなため、両者を区別する
判断基準を明文化し、以降のspecでの再検討コストを減らす]

## 背景・発端

`entry-auto-category-2026-27` タスク2.1（エントリー時カテゴリー連動）の実装レビューで、
「選手がエントリー先と同じ系統側に、対応するカテゴリーとは異なるカテゴリーを保有している
場合は新規付与を見送る」というガード（Requirement 11、既存不整合への不介入を定めた
Requirement 7.1の精神を踏まえて追加）を実装する過程で、「選手が同系統側に**複数の**
カテゴリーを保有しており、その中に正しい対応先が含まれる場合（重複保有・同系統内複数保有と
いった既存不整合と同席するケース）」の扱いが論点になった。

初期実装は「保有集合が対応先ちょうど1件でなければ一律見送り」としていたが、人間による判断は
「重複・複数保有そのものには一切介入しないが、その中に正しい対応先が含まれるなら新規付与は
通常どおり実行してよい」というものだった（2026-09-10、entry-auto-category-2026-27
agreement-log.md 決定事項#7参照）。この判断はタスク固有の例外ではなく、Cyclox全体の設計方針
として今後のspecにも適用する。

## 方針

**「既存の不整合データに介入しない」は「既存の不整合データそのものを変更（cancel・修正・削除）
しない」という意味であり、「不整合データが存在する選手に対する、それとは独立した新規処理
（新規付与・新規作成等）を一律に見送る」という意味ではない。**

不整合の有無を確認する目的が「新規処理を実行してよいかの判定材料」である場合、判定は
以下の基準で行う:

- **既存の不整合行（重複・対応外ペア・同系統内複数保有等）そのものは一切変更しない**
  （cancel・修正・削除いずれも行わない）。これは常に不変の制約。
- **新規処理の可否判定は「集合の中に、判定したい値が1つでも含まれるか」（存在判定）で行い、
  「集合がその値ちょうど1件だけか」（完全一致判定）では行わない。** 同席する他の不整合な値の
  存在は、新規処理の可否に影響させない。

## 判断基準（この方針を適用してよいかの目安）

以下の条件を両方満たす新規処理には、この方針（存在判定・介入せず進行）を既定として適用する:

1. **既存データを一切変更しない。** 新規行の追加のみで完結し、既存の不整合行への
   cancel・修正は伴わない。
2. **誤って実行されても実害が小さく、事後に是正可能。** 業務の継続（エントリー成立・
   大会参加・リザルト記録等）を妨げず、是正バッチ等（catracer-cleanup-2026-27のような
   後続の是正処理）で事後訂正できる。

逆に、新規処理が既存データの変更を伴う場合や、誤って実行された場合の実害が大きく事後訂正が
困難な場合（例: 不可逆な通知の送信、課金、外部システムへの連携等）は、この既定を機械的に
適用せず、都度の要件定義で明示的に判断する。

### 補足: 有効期間（apply_date/cancel_date等）を持つデータへの存在判定の注意点

**【2026-09-13追記】** `entry-auto-category-2026-27` タスク2.1の実装レビューで、存在判定
（上記②）の対象データが `apply_date`/`cancel_date` のような有効期間を持つ場合、「ある時点の
スナップショット」だけを見て判定すると、**判定直後に効力を持つ既知の遷移（未来日で既に
登録済みの切替予定）との将来的な衝突を見落とす**ことがあると判明した（詳細:
entry-auto-category-2026-27 agreement-log.md 決定事項#9）。

この種のデータでは、以下のいずれかを個別に検討すること:
- 遷移予定が実運用でどの程度の頻度・確度で発生するか（コード上その遷移を生成する仕組みが
  実在するか、実データに実例があるか）を調査し、発生確率が十分低ければ、上記②の実害小・
  事後是正可能の基準内として残存リスクを受容してよい（受容する場合は要件文書に明記する）。
- 発生頻度が無視できない、または実害が大きい場合は、判定基準時点のスナップショットだけでなく
  「新規処理の結果が既知の未来の遷移と衝突しないか」も併せて確認するロジックを追加する。

いずれにせよ、「発生しうるかどうか調査せず、機械的に存在判定だけで押し通す」ことは避ける。

### 補足: 重複防止ガードの「自己観測性」

**【2026-09-25追記】** `lineage-propagation-idempotency-2026-27` で、有効期間を持つ行を作成する
処理が**自分自身の書き込みを自分の重複防止判定で観測できない**という欠陥が実運用で顕在化した
（リザルトの再取込のたびに連動先カテゴリーが1行ずつ増え、5選手・8行の重複が発生）。

機序は単純である。重複防止の検索が `apply_date <= $atDate` を条件にしていた一方、その検索を
通過して作成される行の `apply_date` は `$atDate + 1日` だった。作成される行は必ず検索窓の外に
落ちるため、同じ処理を2回走らせると毎回「まだ無い」と判定して作り足す。

混入経緯にも再現性のある教訓がある。この不一致は、日付規約を「呼び出し元が+1日済みの値を渡す」
から「呼び出し先が内部で+1日する」へ変更した際に生まれた。**変更は書き込み経路にだけ適用され、
読み取り経路（重複防止の検索窓）は引数経由でタダで受け取っていたぶんを静かに失った。**
同じコミットは整合性検知側の基準日は正しく追随させており、同一コミット内で読み手が分かれていた。

したがって、以下を検証観点とする。

1. **自己観測性の確認。** 有効期間（`apply_date`/`cancel_date`等）を持つ行を作成する処理を書く/
   変更するときは、「この処理をもう一度同じ引数で走らせたら、自分が作った行を自分のガードが
   見つけられるか」を必ず確認する。日付の窓と、書き込む行の日付が一致しているかを突き合わせる。
2. **日付規約を変えたら読み手を全数点検する。** 書き込む日付の決め方を変更する場合、その日付を
   読む側（重複防止・終了処理・検知・集計）を洗い出し、それぞれ追随が必要かを判断した記録を残す。
   「書き込み側だけ直して読み取り側は据え置き」は、同一コミット内でも起こりうる。
3. **判定処理を別用途へ流用したら、流用元も逆照合する。** 既存の判定ヘルパーを新しい用途へ
   転用して欠陥が見つかった場合、「流用先だけ直して元のヘルパーは残置」で終わらせない。元の
   用途でも同じ欠陥が成立しないかを確認する。実際、本件の欠陥は先行specのレビューで流用先
   （エントリー補完）について指摘され修正されていたが、流用元（昇格連動）は点検されず残った。
4. **重複防止に日付の窓を使ってよいかを用途で判断する。** 「その時点で何を保有していたか」を
   問う判定に日付窓は正しい。「この処理が既に結果を書いていないか」を問う判定に日付窓を使っては
   ならない。後者は、書き込みを一意に識別できるキー（対象・由来・理由など）で判定する。
   なお、そのキーには**実行のたびに変わりうる識別子を含めない**（本件では、再取込のたびに
   作り直されるリザルトidを冪等キーに含めると修正が機能しなくなる関係にあった）。

## 「見送り一辺倒」を避ける理由

- **見送りは運用上の不透明さを生む。** 「なぜ自動処理が発火しなかったのか」を利用者が
  事後に追跡する必要があり、無関係な既存不整合が原因で新規処理まで止まっていると誤解を招く。
- **既存の設計哲学と整合する。** `CategoryLineageLinker`の対応ペア判定（`isValidActiveSet()`）
  も、対応表対象外カテゴリー（女子系統等）が同席していてもペア判定自体は継続する設計になって
  おり、「無関係な要素の同席を理由に判定全体を止めない」という考え方を既に採用している。
- **ブラスト半径の抑制という当初方針との整合。** 選択肢B（エントリー時オンデマンド付与）採用の
  根拠は「対応する新規付与1件分にブラスト半径を抑えつつ、既存不整合には非破壊的に振る舞う」
  ことであり、「既存不整合を理由に新規付与そのものを止める」ことまでは求めていない。

## 適用例

- `entry-auto-category-2026-27` タスク2.1: エントリー先と同じ系統側の保有確認で、保有集合に
  重複・複数保有が含まれていても、その中に対応先カテゴリーが1つでも含まれていれば新規付与判定
  を継続する（`CategoryLineageLinker::supplementPairedCategoryOnEntryRegistration()`）。
- `lineage-propagation-idempotency-2026-27` タスク2.1/2.2: 相手系統の保有判定から日付の上限窓を
  外し（自己観測性の回復）、当該取込が自ら作成した行の後始末を追加した
  （`CategoryLineageLinker::propagateLinkedPromotion()`）。
