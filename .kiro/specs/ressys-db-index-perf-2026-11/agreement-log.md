# ressys `/race/{id}` 遅延調査 — 合意ログ

- 作成日: 2026-11-14 / 対象: `cyclox2ressys_svr`（`cyclox2res_sys`）、DB=`cyclox2`（MySQL 5.7）
- 区分: 調査・設計・ローカル検証のみ（**本番DBへは一切変更していない**）。Tier 2相当（DBスキーマ変更案を含むため）。

## 経緯と合意
1. 依頼: ローカルで `/race/{ecat_id}` が約12秒かかる。外部キー列の索引不足が疑われるため、索引追加案を設計・検証する。
2. 人間より「本番ではここまで重くない」との指摘 → 痕跡調査を実施（下記）。
3. 人間が本番で `SHOW INDEX` 相当を実行し結果を提供（`evidence/prod_show_index_2026-11-14.txt`）。
4. 結果、**主要な外部キー列は本番に索引済み**と判明。計画を縮小することで合意:
   「ローカルへ本番同等の索引を追加→前後計測→元に戻す→文書化」。本番への索引追加は提案しない（任意の小項目のみ別途判断）。

## 痕跡調査の結果
- 2025-01-09 `ef01214`（PR #3 `speedup_race_result`, 2025-08-22 マージ）: `Categoryracer_model::get_rankuppers_of_ecat` の
  5段JOINが「本番環境で激重」だったため3段+2段にSQL分割。→ 過去に本番でも重い箇所があり、対策はSQL分割（索引追加ではない）。
- キャッシュ実装の痕跡なし（CI標準のcache設定のみ、`cache_on=FALSE`、Apacheに Expires/Cache-Control なし、CakePHP core.php も標準）。
- リポジトリ内に ALTER/ADD INDEX の記録なし。本番の索引は手作業で追加された可能性が高い（名前が不揃い: `in_result_id`, `index_entry_cat_id` 等）。

## 結論
- ローカルの約12秒は、**ローカルDB（本番の古いコピー）に索引が欠けている**ことが原因。本番の問題ではない。
- 本番同等の4索引をローカルに追加すると 12.1秒 → 約0.5秒、本番に無い4索引も加えると約0.24秒（`test-results.md`）。
- 本番の索引は既に十分。追加で効果があるのは小テーブルの4列のみで、緊急性は低い（`proposed-index.sql` 参照、適用は人間判断）。

## 影響評価（cyclox-web／書き込み）
- 追加候補の索引サイズ合計は約3.4MB（本番同等4索引は既に本番にある）。書き込み増は、対象が小テーブル（最大約3.9万行）の単一列索引のため無視できる範囲。
- cyclox-web（CakePHP）はアプリコード・テストとも索引の有無に依存しない（スキーマは ER の SQL 由来で索引は PRIMARY のみ。fixture 等に索引定義なし）。
  ただし新規に環境を `cyclox2ER.sql` から構築した場合は、**本番の4索引が再現されない**点に注意（開発DBが遅くなる原因そのもの）。
