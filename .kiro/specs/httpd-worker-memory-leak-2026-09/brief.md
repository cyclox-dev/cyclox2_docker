# Brief: httpd-worker-memory-leak-2026-09

## Problem

`cyclox2_svr`コンテナ内のApache（prefork MPM）ワーカープロセスが、長期稼働（起動から約1週間程度）で
異常に肥大化し、Docker Desktop全体のメモリ（7.65GB）を圧迫していた。2026-09-09、
`entry-auto-category-2026-27`spec実装前の環境確認中に、テスト実行がトリガーとなって
`cyclox2_mysql`コンテナがOOM Killされる事象として顕在化した。

## Current State（2026-09-09調査で確認した事実）

- **単一ワーカーの異常な肥大化**: `docker exec cyclox2_svr ps aux`で、同時期に起動した複数の
  httpdワーカーのうち1プロセス（PID 20）だけが**RSS約3GB（全体メモリの37.2%）**に達していた。
  他の兄弟ワーカーは同じ起動時刻でも15〜20MB程度に留まっていた（`docker stats`実行時点の
  スナップショット。起動時刻はプロセスのSTART列で09-02と確認）。
- **1リクエストの上限では説明できない**: `php -i`で確認した`memory_limit`は**128M**。単発の
  重い処理では3GBに到達し得ず、**複数リクエストをまたいでメモリが解放されず蓄積した**ことを
  示唆する。
- **ワーカーのリサイクル設定が存在しない**: `/etc/httpd/`配下を`MaxConnectionsPerChild`・
  `MaxRequestsPerChild`で検索したが、どこにも設定が無い（Apacheのデフォルトである
  「無制限＝ワーカーは再起動されるまで永久に生き続ける」が適用されている）。通常はこの値を
  設定し、定期的にワーカーを再起動してメモリの蓄積を強制リセットするのが定石だが、その安全弁が
  存在しない。
- **他の主要リーク源は消去法で除外済み**:
  - DB接続: `app/Config/database.php`で`persistent => false`（永続接続はもともとoff）
  - opcache: `opcache.memory_consumption = 128`（共有メモリ上限あり、プロセスRSSとは別区分）
- **単一ワーカーにのみ発生している点が重要な手がかり**: 全リクエストに共通する基礎的なリークで
  あれば、同程度稼働している他のワーカーも同様に肥大化するはず。実際には1プロセスのみが突出して
  おり、**特定の処理・コードパスが繰り返しそのワーカーに割り当たった時にのみ発生している**
  可能性が高い。原因のコードパスは未特定。
- 応急対応として`cyclox2_svr`・`cyclox2ressys_svr`コンテナを再起動し、メモリを解放済み
  （3GB超→45MB程度）。根本原因は未解決のまま。

## Desired Outcome

- 肥大化を引き起こしている具体的なコードパス（画面・API・バッチのいずれか、および処理内容）を
  特定する
- 再発防止策を決定する（該当コードの修正、または`MaxConnectionsPerChild`設定によるワーカー
  リサイクルの導入、あるいはその両方）
- 恒久対応後、長時間稼働させても単一ワーカーの異常な肥大化が再発しないことを確認する

## Approach（未検討・要調査）

- Xdebugのプロファイラ、または`memory_get_peak_usage()`を要所に仕込んだ簡易計測で、
  疑わしいエンドポイント（大量データを扱う画面・レポート生成・一括処理系のAPI）を特定する
- 特定できたら、該当コードのオブジェクト参照・静的プロパティ・キャッシュ蓄積等を確認する
- 恒久対応の選択肢（コード修正 vs `MaxConnectionsPerChild`導入 vs 両方）は原因特定後に判断する

## Scope

- **In**:
  - `cyclox2_svr`コンテナ内のhttpdワーカーメモリ肥大化の原因調査
  - 再発防止策の検討・実装
- **Out**:
  - `cyclox2_mysql`・`cyclox2ressys_svr`等、他コンテナの個別のメモリ特性調査（今回`cyclox2_svr`
    再起動で`cyclox2ressys_svr`も合わせて再起動したが、後者側で同様の異常肥大化を確認した
    わけではない。必要であれば別途調査）
  - Docker Desktop自体のメモリ割当設定変更（インフラ設定であり本specの対象外）
  - `entry-auto-category-2026-27`等、進行中の機能開発spec — 本問題は環境調査中に偶発的に
    発見された既存の運用課題であり、機能開発とは独立

## 発見の経緯

`entry-auto-category-2026-27`spec（エントリー時ME⇔MM対応ペア自動付与）の実装着手前の環境確認
（テストベースライン確認）中に、テスト実行がトリガーとなって`cyclox2_mysql`がOOM Killされた
ことで発覚した。詳細な調査ログ・対応履歴はentry-auto-category-2026-27のセッション記録を参照
（本specはその過程で見つかった独立の課題を切り出したもの）。
