# Implementation Plan

- [ ] 1. 基盤整備: テストデータとME⇔MM対応表の単一定義
- [ ] 1.1 選手・カテゴリー認定関連のテストデータ基盤を整備する
  - `Category`（C1〜C4, CM1〜CM3, CL1〜CL3, WM等の代表カテゴリー）・`CategoryRacer`・`Racer`・
    `HoldPoint`の各モデルについて、テストで繰り返し使える代表データ定義を用意する
  - 有効保有（cancel_date未設定）・終了済み（cancel_date設定済み）・論理削除済みの3パターンを
    再現できるデータを含める（元ME1判定など履歴参照ロジックのテストに必要）
  - Observable: 新設するテストケースがこのテストデータ定義を読み込んで、選手のカテゴリー認定状態を
    任意のパターンで再現できる
  - _Requirements: 1.1_

- [ ] 1.2 ME⇔MM対応表を単一の定義として実装する
  - ME1〜ME4とMM1〜MM3の対応関係（ME4⇔MM3、ME3⇔MM2、ME2⇔MM1、ME1⇔MM1）を1箇所で保持し、
    カテゴリーコードから対応する相手系統カテゴリーを取得できるようにする
  - 女子系統（CL1〜CL3、WM）等、対応表の対象外カテゴリーを渡した場合は対応先が無いことを表す
    結果を返すようにする
  - 対応表の全パターン・対象外パターンを網羅するテストを先に書いてから実装する
  - Observable: 各カテゴリーコードに対して対応する相手系統カテゴリー（または対象外を示す結果）が
    一意に返る
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 9.1_

- [ ] 2. 対応表を用いた判定・連動ロジック
- [ ] 2.1 対応ペア・単独保有・対応外ペア・重複の判定ロジックを実装する
  - 選手が保有することになるカテゴリー集合が「無保有／単独保有／正当な対応ペア／対応外ペア／
    同一カテゴリーの重複／同系統内の複数保有」のいずれに該当するかを判定できるようにする
  - 対応表の対象外カテゴリー（女子系統等）は対応ペア・対応外ペアの判定対象から除外しつつ、
    重複の判定だけは全カテゴリー共通で行う
  - 各パターンを網羅するテストを先に書いてから実装する
  - Observable: 単独保有・正当ペア・対応外ペア・重複・同系統内複数保有それぞれの入力に対して
    判定結果が期待通りに分かれる
  - _Requirements: 2.1, 2.2, 2.3, 3.1, 3.2, 3.4, 3.5, 3.6, 9.1, 9.2_
  - _Depends: 1.2_

- [ ] 2.2 元ME1判定ロジックを実装する
  - 選手のカテゴリー認定履歴（論理削除された行を含む全履歴）から、過去にME1を有効保有していた
    ことがあるかを判定できるようにする
  - 元ME1歴がある選手・ない選手・ME1を保有したが後に取り消された選手のパターンを網羅するテストを
    先に書いてから実装する
  - Observable: 過去にME1保有歴がある選手とない選手とで判定結果が正しく分かれる
  - _Requirements: 5.1_
  - _Depends: 1.1_

- [ ] 2.3 系統間連動時の連動先カテゴリー解決ロジックを実装する（ME1特例込み）
  - 昇格が発生したカテゴリーから、選手が保有する相手系統の連動先カテゴリーを対応表に基づいて
    解決できるようにする
  - 連動更新先がME1に該当し、かつ選手が元ME1でない場合はME2へフォールバックするようにする
  - 相手系統を保有していない場合は連動先が存在しない旨を返すようにする
  - ME1特例の成立・不成立双方のケースを含むテストを先に書いてから実装する
  - Observable: マスターズ側がMM1へ昇格した際、元ME1選手の連動先はME1に、元ME1でない選手の
    連動先はME2になる
  - _Requirements: 4.3, 5.2, 5.3, 5.4_
  - _Depends: 2.1, 2.2_

- [ ] 2.4 系統間連動の保存実行ロジックを実装する
  - 相手系統の連動先カテゴリーが解決できた場合に、相手系統の現在有効なカテゴリーを終了させ、
    新しい連動先カテゴリーを付与する一連の保存を実行できるようにする
  - 相手系統を保有していない選手には新規付与を行わないようにする
  - 昇格実績（保持ポイント相当の記録）は連動更新によって複製しないようにする
  - 連動更新の実行前後で対応ペア・単独保有の判定ロジック（2.1）を満たすことを確認するテストを
    先に書いてから実装する
  - Observable: 相手系統保有選手は連動保存後の状態が対応表上の正当な状態になり、相手系統未保有の
    選手には連動保存が発生しない
  - _Requirements: 4.1, 4.2, 4.4, 4.5, 4.6_
  - _Depends: 2.3_

- [ ] 2.5 統合後カテゴリー集合の一括検証ロジックを実装する
  - 選手コードを指定して、その選手が現在有効保有するME/MMカテゴリー集合全体が対応表・重複ルールに
    合致するかを検証できるようにする
  - 3カテゴリー以上の有効保有や対応外ペアを含む集合を渡した場合に検証が失敗することを確認する
    テストを先に書いてから実装する
  - Observable: 正当な集合（無保有／単独保有／正当ペア）は検証に成功し、不正な集合は検証に失敗する
  - _Requirements: 8.1, 8.2_
  - _Depends: 2.1_

- [ ] 3. カテゴリー認定情報の保存時バリデーションを追加する
  - `CategoryRacer`の保存に、同一カテゴリーの重複付与の拒否と、対応外ペアを生む保存の拒否を追加する
  - カテゴリーの終了処理のみ（cancel_dateの設定のみ）を行う保存はこのバリデーションの対象外とする
  - バリデーションエラー時に、操作者が拒否理由を理解できるメッセージを返すようにする
  - 既存の保存経路（レース結果昇格、系統切替、選手統合、その他手動付与）を代表するシナリオで、
    対応外ペア・重複を生む保存がエラーになり、正当な保存は成功し続けることを確認するテストを
    先に書いてから実装する
  - Observable: 対応外ペアまたは重複を生む保存呼び出しがエラーとなり、理由が分かるメッセージが
    返る。既存の正当な保存呼び出しは引き続き成功する
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 9.1, 9.2_
  - _Boundary: CategoryRacer model_
  - _Depends: 2.1_

- [ ] 4. リアルタイム昇格の系統間連動統合
- [ ] 4.1 (P) エリート系統昇格時のマスターズ側連動を統合する
  - エリート系統でのレース結果による昇格が発生した際に、系統間連動の保存実行ロジックを呼び出し、
    選手が有効保有するマスターズ側カテゴリーを対応表に沿って追随更新する
  - 既存の昇格判定・cancel処理・保持ポイント付与ロジックの分岐は変更しない
  - Observable: エリート側がC3からC2に昇格した際、マスターズ側でCM2を保有していた選手は
    CM1に連動更新される
  - _Requirements: 4.1, 4.4, 4.6, 5.2_
  - _Boundary: ResultParamCalcComponent_
  - _Depends: 2.4, 3_

- [ ] 4.2 マスターズ系統昇格時のエリート側連動を統合する
  - マスターズ系統でのレース結果による昇格が発生した際に、系統間連動の保存実行ロジックを呼び出し、
    選手が有効保有するエリート側カテゴリーを対応表・ME1特例に沿って追随更新する
  - 既存の昇格判定・cancel処理・保持ポイント付与ロジックの分岐は変更しない
  - Observable: マスターズ側がCM2からCM1に昇格した際、元ME1でない選手のエリート側はC2に、
    元ME1選手のエリート側はC1に連動更新される
  - _Requirements: 4.2, 4.3, 4.6, 5.3, 5.4_
  - _Boundary: ResultParamCalcComponent_
  - _Depends: 2.4, 3_

- [ ] 4.3 単独保有時の非付与と昇格実績の重複防止を確認する統合テストを追加する
  - 相手系統を保有しない選手が昇格しても新規カテゴリーが付与されないこと、系統間連動が発生した
    昇格で昇格実績（保持ポイント相当の記録）が重複して記録されないことを、エリート・マスターズ
    双方の昇格経路で確認する
  - Observable: 単独保有選手の昇格結果に相手系統の新規カテゴリー行が生成されないこと、連動が
    発生した昇格で昇格実績の記録が1件のみ生成されることがテストで確認できる
  - _Requirements: 4.4, 4.5_
  - _Boundary: ResultParamCalcComponent_
  - _Depends: 4.1, 4.2_

- [ ] 5. (P) 系統切替操作を対応表準拠に改修する
  - 系統切替の対応先候補を、単一の対応表定義から取得するように変更する
  - 切替実行時に反対系統の有効カテゴリーを無条件かつ一括で終了させるのをやめ、対応表上の正当な
    ペアにならないもののみを終了対象とするように変更する（既に正しいペアになっている反対系統
    カテゴリーは終了させない）
  - ME1特例を満たさない選手がC1への切替を試みた場合にエラーで拒否されることを確認する
  - 対応ペア補完・特例対応ツールとしての役割再定義に合わせて、操作画面の説明文言を更新する
  - 上記シナリオを網羅するテストを先に書いてから実装する
  - Observable: 対応ペアの一方のみを保有する選手への切替は正当なペアとなる場合のみ許可され、
    既に正しいペアを保有する選手への切替操作では既存の正しいペアが解除されない
  - _Requirements: 6.1, 6.2, 6.3, 6.4_
  - _Boundary: CategoryRacersController change_em_
  - _Depends: 1.2, 3_

- [ ] 6. (P) シーズン参照バッチ処理を両系統出走に対応させる
  - シーズン参照バッチ処理が「シーズン最初の出走のみ」でエリート／マスターズを判定している既存
    ロジックを、「シーズン中の全出走を見てエリート・マスターズ双方への出走があるか」を判定する
    ロジックへ変更する
  - 両系統に出走した選手向けの区分値を新たに記録できるようにする（既存のシーズン別記録の
    データ構造は変更しない）
  - 片方のみ出走・両方出走・出走なしの各パターンを網羅するテストを先に書いてから実装する
  - Observable: 同一シーズンにエリート・マスターズ双方へ出走した選手の記録が「両方」を表す値に
    なり、片方のみ出走した選手は従来通りの値になる
  - _Requirements: 7.1, 7.2_
  - _Boundary: CatLimitShell, EntryCatLimit_
  - _Depends: 1.1_

- [ ] 7. (P) 選手統合処理に統合後の整合性チェックを追加する
  - 選手統合処理の実行後、統合先選手が有効保有することになるカテゴリー集合を検証し、対応外ペアや
    重複が生じる場合は統合操作全体を失敗させ、統合前の状態に戻すようにする
  - 統合元・統合先が同一カテゴリーを共に有効保有していたケースを含めて検証する
  - 正当な統合（対応外ペア・重複を生まない）と不正な統合の両方を網羅するテストを先に書いてから
    実装する
  - Observable: 対応外ペアや重複が生じる統合を実行すると統合処理全体が失敗し、統合前の状態が
    保持される。正当な統合は従来通り成功する
  - _Requirements: 8.1, 8.2_
  - _Boundary: OrgUtilController uniteRacer_
  - _Depends: 2.5_

- [ ] 8. 結合シナリオの検証
  - レース結果による系統間連動昇格、系統切替による対応ペア補完、選手統合の各操作を組み合わせた
    代表シナリオで、いずれの操作後も選手のカテゴリー保有状態が対応表・重複ルールに反しないことを
    確認する
  - 既存不整合データを模したケース（対応外ペアを既に保有する選手）に対して連動・切替・統合の
    各操作を行った場合に、新たな不整合を生まずエラーで拒否されることを確認する
  - Observable: 複数操作を連続して行う結合シナリオテストが全て成功し、対応外ペア・重複が
    発生しうる操作は必ずエラーで止まる
  - _Requirements: 2.1, 2.2, 2.3, 3.1, 3.2, 3.4, 3.5, 3.6, 4.6, 8.1, 8.2_
  - _Depends: 3, 4.1, 4.2, 4.3, 5, 6, 7_
