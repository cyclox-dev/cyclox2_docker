# 引き継ぎ資料: AJOCCシーズン実績レポート「Web閲覧数」自動化のための技術情報

作成日: 2026-08-09
作成元: `ajocc-report-2025-26`（2025-26シーズンレポート作成タスク、PR #29/#35で完了）
引き継ぎ先: Issue #37「AJOCCシーズン実績レポートの自動作成」（GA4 Data API エージェント接続計画）

---

## 1. 背景

2025-26シーズンレポートでは、Web閲覧数（P.3/P.4/P.14/P.15）のデータをユーザーが手動でGA画面から
エクスポートしたExcel（`25-26ReportData.xlsx`、git管理外・個人所有）を提供し、エージェントが
その内容を`dataset_2526.json`へ手動でマッピングする形で対応した（Phase 4-6、2026-07-19）。
本資料は、この手動フローをGA4 Data API経由の自動取得に置き換える際に必要な技術情報をまとめる。

## 2. レポートのデータフロー（現状）

```
[ユーザー: GA画面からExcelエクスポート]
        ↓
[エージェント: Excelをシート単位で読み取り、dataset_2526.jsonへ手動マッピング]
        ↓
[dataset_2526.json（数値の唯一の正）]
        ↓
[build_report.js（node）: JSONを読み込み15ページPPTX生成、数値ハードコードなし]
        ↓
[rebuild.sh: PPTX→PDF変換、QA用PNG生成]
```

自動化のゴールは「ユーザーのExcelエクスポート」ステップを「エージェントによるGA4 Data API直接クエリ」に
置き換えることであり、`dataset_2526.json`のスキーマと`build_report.js`のレンダリングロジックはそのまま
再利用できる設計になっている（決定#11の「JSON差し替え→再ビルド」設計が起点）。

## 3. `dataset_2526.json`のWeb関連フィールド仕様

### p3.web_view / p4.web_view（月平均ビュー数、単一指標）
```json
{"label": "月平均 ビュー数", "value": 94525, "note": "...", "provisional": false, "source": "ga"}
```
- `provisional: true`にすると「（仮値）」表記、`false`で確定値表記になる（`build_report.js`側の分岐）。
- p4側は`y2324`/`y2425`/`y2526`/`yoy_delta`/`col_source`/`provisional`/`note`を持つ4列比較形式。

### p14.rows（24行のページ階層別ビュー推移表）
各行は`{parent, child, y2324, y2425, y2526, yoy_pct}`。特殊値:
- `y2526`/`yoy_pct`が数値 → 通常描画
- `y2526`が`"集計不能"`（文字列）→ イタリック表示（GA4で分離取得できない場合に使用）
- `yoy_pct`が`"-"`（文字列）→ 前年度比を「-」表示（集計方法が異なり比較不可の場合に使用）
- 行に`"highlight": true`を追加 → 行全体を`SH_ORANGE`で網掛け

### p15.tables（4つのランキング表）
各テーブルは`{title, columns, rows, placeholder}`。`rows`は`{rank, title, views}`の配列。

## 5. 重要な発見: GA4「その他」バケット問題（自動化前に要対応）

2025-26シーズン分のエクスポートでは、`その他`列（期間合計279,737）が
**D〜Q列の他カテゴリすべてを合計した値とC列（総計）の差分に完全一致**することを確認した
（`その他` = 総計 − 個別カテゴリ合計）。これは、リザルト・ランキング・選手検索・選手データの
4カテゴリ（P.14の9行分）が、現在のGA4プロパティ設定では**個別のコンテンツグループ／カスタム
ディメンションとして定義されておらず、`(other)`相当のバケットに一括計上されている**ことを意味する。

24-25シーズン以前（`tmp/24-25_AJOCC_report .pdf` P.14）はこれらのカテゴリが個別集計できていたため、
**過去のGA/GA4設定では存在した分類定義が、現行のGA4プロパティでは失われている（または移行時に
引き継がれなかった）可能性が高い**。

参考: リザルト/ランキングのページはURLパターンが把握できている（本タスクでユーザーが追加提供した
「リザルト」「ランキング」シートのTop10データより）:
- リザルト: `https://data.cyclocross.jp/race/<id>`
- ランキング: `https://data.cyclocross.jp/ajocc_ranking/<...>` および `https://data.cyclocross.jp/point_series/<id>`
- 選手検索・選手データのURLパターンは今回のExcelには含まれておらず未確認（別途調査要）。

**自動化に着手する前に、GA4管理画面（またはGA4 Data APIの`pagePathPlusQueryString`ディメンション＋
正規表現フィルタ）で上記パスパターンを識別できるコンテンツグループ／カスタムディメンションを
設定する必要がある。** 設定できれば、Data API経由でリザルト/ランキング/選手検索/選手データの
9行も自動集計可能になり、P.14の「集計不能」表記を解消できる。

## 6. 集計期間・方法論に関する注意点

- 2025-26シーズンのGAデータは**2025/9/1〜2026/3/31（7ヶ月）**のみ取得可能だった（シーズン境界は
  本来2025/4/1〜2026/4/1）。トラッキング開始時期または対象プロパティの制約と推測されるが未確認。
  自動化時はGA4側のデータ保有開始日を確認し、可能なら通年（4月〜翌3月）に拡張すること。
- 「カレンダー/過去」「ニュース/過去」の2行は、23-24/24-25（PDF転記値）と25-26（GA4実データ）で
  **集計方法が異なる可能性が高く、数値の桁が大きく異なる**（前者は数百〜数千、後者は数万）。
  今回は値をそのまま表示しつつ前年度比を「-」にして回避したが、根本原因（GA4側の計測方法変更、
  あるいはページ構造変更によるURL集約範囲の違い等）は未調査。自動化時に同じ現象が再現するか
  確認し、原因を特定できればyoy_pctの自動判定ロジック（閾値超えたら比較除外、等）に落とし込める。
- Web閲覧数以外（DB集計：エントリー数・選手数等）は`cyclox2_svr`のMySQLから直接抽出しており、
  本資料の対象外（`runbook.md`参照）。

## 7. Issue #36（Xserver側GA4タグ導入）との関係

Issue #36は「AJOCC本体ページ（Xserver管理・MovableType想定）にGA4タグが未導入」という**別ドメイン・
別問題**。本資料5節の「その他バケット」問題は、**data.cyclocross.jp側（既にGA4タグ導入済み）の
コンテンツグループ設定不足**であり、Issue #36の対象範囲外。両者は独立して対応が必要:
- Issue #36: Xserver側ページのGA4タグ新規導入（現在ゼロから計測不可）
- 本資料5節: data.cyclocross.jp側の計測済みデータの分類粒度改善（計測はできているが分類が粗い）

自動化が完全なレポートを生成するには、両方の対応が前提条件になる可能性が高い
（Xserver側ページがP.3/P.4のWeb閲覧数のどの部分に寄与しているか要確認）。
