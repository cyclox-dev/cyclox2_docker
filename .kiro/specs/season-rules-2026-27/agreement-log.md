## 壁打ち概要

AJOCC 2026-27規則改正（https://www.cyclocross.jp/news/2026/07/20262027amendment.html）対応
プロジェクトの一部として、昇格・残留・降格のルール値と判定方法の変更を扱う。
ディスカバリーセッション（roadmap.md / brief.md）で以下を整理済み：

- 対応は二層：(a) リアルタイム昇格枠（MM2→MM1=最大3名）はアプリコード
  （`ResultParamCalcComponent`）のシーズン切替パターンで対応、(b) シーズン末残留・降格判定は
  `rider-demotion-2025-26` の runbook/SQL 資産を新ルール対応版に改訂
- 系統横断残留判定は upstream spec `me-mm-linkage-2026-27` の対応表を前提とする（重複定義禁止）
- 2026-27シーズン末降格の本番実行（2027-03）はスコープ外（人間が runbook に従い実施）
- 期限 2026-07-31（判定ロジック実装・runbook 改訂・ローカル検証完了まで）

## 2026-08-29 タスク1（MM2→MM1昇格上限3名化）実装完了・公式改正文との照合結果

AJOCC公式ルールページ（https://www.cyclocross.jp/about/rules-regulations.html）と照合し、
MM2→MM1（実装上はCM2→CM1・CM2+3→CM1）の出走人数区分別昇格枠を確定した：

| 出走人数 | 昇格人数 |
|---|---|
| 1〜4名 | 0名 |
| 5〜9名 | 1名（同一シーズン内で2回対象となると昇格確定。既存の「少人数2勝」ロジックが
  CM2/CM2+3を含めて対応済みのため変更不要） |
| 10〜19名 | 1名 |
| 20〜29名 | 2名 |
| 30〜39名 | 2名 |
| 40〜49名 | 3名（← 26-27シーズンでの変更点。旧基準は2名のまま） |
| 50名〜 | 3名（← 同上） |

この確定値は、既存の`__rule0123`（40人以上→3名、20人以上→2名、10人以上→1名）と数値が
完全一致したため、新規配列を追加せず`__rule0123`を再利用した（design.md L316の仮称
`__rule26mm`は不採用。既存配列の再利用は本ファイルの既存規約——`__rule012333`が複数
カテゴリー・複数シーズンで再利用されている——と整合する）。

`_isSeasonAfterEq2627()`（大会開催日2026-04-01以降）を追加し、`__setupRankUpRules()`の
最上位分岐として2026-27ルールを追加（CM2/CM2+3のみ`__rule0123`へ差し替え、他カテゴリーは
24-25分岐の複製）。TDD（境界日2026-03-31/2026-04-01、境界人数39/40人、CM2+3の同一ルール
適用を含む6ケース）で先にRED→実装後GREENを確認。

既存17スイート・222テスト全GREEN（回帰なし）。「5-9名2勝」の少人数昇格ロジック
（`ResultParamCalcComponent.php` 414行目付近）はCM2/CM2+3を既に含んでおり、シーズンに
かかわらず動作するため本改訂の対象外（変更不要）。

なお、女子エリート（WE2→WE1）の勝利数ベース昇格ロジックも同様に公式改正文と照合し、
実装（`CL2`/`CL2+3`の10人以上1勝・5-9人2勝ロジック）が一致していることを別途確認済み
（変更不要）。

## 2026-08-29（続き）独立レビューでの指摘6件・4件対応

独立レビュアー（reviewer subagent、全18スイート実機実行・n=1〜60の網羅検算込み）による検証で
6件の指摘を受け、うち以下を対応した。

1. **【中・対応済み】`__rule0123`再利用による意図しない結合**: 新設した26-27ルールの値が
   既存の`__rule0123`と一致したため当初これを再利用したが、`__rule0123`はCM1+2+3レース
   （16-17シーズン以降の全シーズン、636行目付近の独自経路）および17-18/18-19シーズンの
   C3/C4/C3+4（2040-2042行目付近）でも共有参照されていることが判明した。値が一致していても
   共有すると、将来どちらか一方だけ改定された場合に無関係な既存経路の挙動まで変わってしまう
   （Requirement 6.3「値の置換のみで対応できる状態を維持する」に反する）。専用配列
   `__rule012233_2627`を新設し分離した。
2. **【低〜中・記録訂正】agreement-log「5-9名2勝はCM2/CM2+3を含めて対応済み」の記述**:
   実コードを再確認したところ、少人数（5-9名）2勝ルールの`CM2+3`分岐（454-458行目付近）は
   「選手が既にCM2を保有している場合はCM2+3レースでの勝利をカウントしない」という既存の
   ガードがあり、MM2所属選手がCM2+3混走レースで2勝しても昇格しない。これは本改訂による
   回帰ではなく設計スコープ外の既存挙動（design.md L298で少人数昇格特例は対象外と明記）
   だが、「対応済み」という記述は実態より広かったため訂正する。AJOCCの意図がCM2+3混走でも
   救済することであれば、別途人間の確認が必要（未対応・要確認事項として記録）。
3. **【低・記録のみ】`__atDate`空時のフォールバック挙動**: `_isSeasonAfterEq2627()`も既存の
   `_isSeasonAfterEqXXXX()`群と同じ規約（空の場合はtrue）に従うため、`__atDate`が未設定の
   まま再計算が走った場合、フォールバック先が24-25分岐から26-27分岐に変わる。
   `meets.at_date`はDB上NOT NULL・date型のため発生確率は低く、既存規約と整合するため
   仕様として許容する（コード変更なし）。
4. **【低・対応済み】docコメント文言**: `_isSeasonAfterEq2627()`のdocコメントに「以降」を
   追加し、既存の`_isSeasonAfterEq2425()`等と表記を統一した。
5. **【低・対応済み】テストケースの拡充**: 30-39名・50名以上の区分、および境界日の翌日
   （2026-04-02）のテストケースを追加した。
6. **【中・対応済み】submoduleがmainブランチ上で未コミットのまま作業していた手順違反**:
   `feat/season-rules-2026-27-mm2-cm1-cap`ブランチ（origin/main起点）を切り直した。

修正後、全18スイート・226テスト全GREEN（回帰なし）を再確認済み。

## 2026-08-29（続き）独立レビュー（SQL資産）での指摘9件への対応

タスク2〜4のSQL資産一式（`sql/01_build_demote_set.sql`, `sql/02_gen_koukaku.sh`,
`sql/03_verify.sql`, `runbook.md`, `test-results.md`, `integration-test-checklist.md`,
`tasks.md`, `agreement-log.md`）に対する独立レビュー（reviewer subagent）で9件の指摘を
受け、以下のとおり対応した。

1. **【高・対応済み】開発DBベースライン汚染**: シミュレーションが使用した開発DBに、
   583件の復元対象に含まれない汚染行（2026-08-16/2026-08-24作成、例`CCH-167-0081`）が
   混入していたことが判明。C1（+1）・CM1（+2）の差分は仕様上ありえない方向（C1は救済
   なしのため本来完全一致、CM1の救済は減少方向にのみ働く）であり、この汚染由来と判断。
   test-results.mdに既知の限界として明記し、この+3件を実効果の証跡から除外した
   （C2/C3/CL1の+48件分は改正内容から論理的に説明可能なため結論は維持）。
2. **【高・対応済み】`01_build_demote_set.sql`のシーズンパラメータが2025-26値のまま
   だった**: `@s:=16`, `@pf:='2025-09-01'`, `@pt:='2026-03-31'`（シミュレーション用の
   一時上書き値）が本番デフォルトとして誤って残置されていた。`@s:=17`,
   `@pf:='2026-09-01'`, `@pt:='2027-03-31'`へ修正し、`seasons`テーブルでの実行時再確認を
   促す警告コメントを追加。
3. **【高・対応済み】`apply_date`上限フィルタの欠落**: 候補集合クエリ・救済側JOINが
   `apply_date`の上限を確認しておらず、降格SQL適用後に誤って再実行された場合、未来日の
   新規行を「既に保有済み」と誤認して連鎖的二重降格を招く恐れがあった。全11箇所に
   `apply_date<=@pt`を追加。
4. **【高・対応済み】Requirement 2.4（WE1出走ゲート）未実装**: CL1の判定が順位基準のみで
   出走照合を行っておらず、要件本文（出走していない場合は順位基準にかかわらず降格対象）
   に反していた。順位基準の`COALESCE`判定に出走照合`EXISTS`サブクエリをANDで追加。
5. **【中・対応済み】`03_verify.sql`の重複・破損クエリ**: §4が§2bと完全に重複していた
   ため、§2bの説明に「Requirement 8.3の検証を兼ねる」旨を明記して§4を統合・削除。
   §2c冒頭のクエリが`racer_code`を選択しておらず出力が解釈不能だったため削除し、
   サブクエリ経由の集計クエリのみを残した。`deleted=0`条件を§2a〜§3全体へ追加。
6. **【中・対応済み】シミュレーション時の別コネクション実行ハザード**: REPEATABLE READの
   もとで`03_verify.sql`を別`docker exec`から実行すると未コミット行が見えず「異常なし」
   と誤判定する。runbook.md §6/§7に、同一mysqlセッション内で`SOURCE`実行することを
   必須要件として明記。
7. **【低・記録のみ】C1+CM1連動降格の副作用**: 降格先がC2+CM2となり`CategoryLineageMap`
   上の正当な対応ペアに該当しない状態が生じうる。AJOCC規則上許容される想定内の状態と
   考えられるが、`catracer-cleanup-2026-27`（別spec、未実装）の将来スコープと重なるため、
   runbook.mdの落とし穴セクションに次年度担当者向けの注記を追加した（コード修正ではない）。
8. **【高・対応済み】test-results.mdの手法説明の不備**: DDL（`CREATE`/`DROP TABLE`）を
   TRANSACTION開始前に別ステップで実行していた実際の手順が記述から欠落していた
   （MySQL/InnoDBはDDLで暗黙コミットが発生するため、TRANSACTION内で行うとROLLBACKが
   機能しなくなる）。手法説明を実際の手順に合わせて訂正し、02/03は今回未実行だった旨も
   明記した。また「`_sim`テーブルを残置」という誤った記述を訂正（`_sim`は削除済み。
   実際に残置されていたのはNULLバグ修正前の壊れた実名テーブルであり、本対応の一環として
   `DROP TABLE survive_flags, demote_all;`で削除した）。
9. **【低・対応済み】tasks.mdの矛盾する実装ノート**: タスク1直後に書いたノートが
   「タスク2〜4は今回実装しない」「`HANDOVER-2026-27.md`参照」としていたが、実在しない

開発DBのクリーンアップ（`DROP TABLE survive_flags, demote_all;`）を実施し、`reason_id=4`
該当件数が583件のまま変化していないことを確認済み（本番・開発DBへの影響なし）。
