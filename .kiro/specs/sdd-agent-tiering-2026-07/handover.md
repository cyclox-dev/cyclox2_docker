## 1. 背景・経緯

- cyclox2 の AJOCC 2026-27 ルール改正対応（5 spec のマルチスペック案件）で、
  `/kiro-spec-batch` の Wave 並列実行（3 サブエージェント同時）により
  **セッション利用上限に2回到達**し、エージェントが途中終了した（2026-07-14〜15）。
- 復旧は `SendMessage` によるトランスクリプト再開で行い、コンテキスト再構築なしで
  継続できることを実証。ただし並列構成そのものがトークン消費の主因のため、
  構成を見直し、以下の割当をユーザーが承認した（2026-07-15）。

## 2. 合意済み構成（これが正）

### 運用原則
1. **同時起動はオーケストレーター（本体）＋サブエージェント1体まで**（合計2）。
   並列 Wave・並列ディスパッチは行わず、すべて逐次実行に読み替える。
2. **中断復旧は新規起動ではなく SendMessage 再開**（コンテキスト維持・再調査コスト回避）。
3. **サブエージェントは「要約のみ返却」契約**。生ログ・全文を親コンテキストへ流さない。
4. **最重要ゲートはオーケストレーターが直接検証**（追加エージェントを起動しない）。
5. 途中終了に備え、サブエージェントには「成果物を書けた時点で都度ディスクへ書く」
   進め方をさせる（今回、途中終了でも spec ファイル群はほぼ完成していた＝復旧が容易だった）。

### ロール別モデル割当

| ロール | モデル | 根拠 |
|---|---|---|
| オーケストレーション・承認ゲート・統合判断 | Fable 5（本体） | 全体整合の把握。追加起動なし |
| 調査・コード探索・事実収集 | Haiku 4.5（Explore 型） | 所在特定・構造把握は安価モデルで十分。判断させず事実のみ返させる |
| 実装（TDD・タスク単位） | Sonnet 5 | コード生成の主力。1タスクずつ逐次 |
| 敵対的レビュー（kiro-review） | Sonnet 5（実装と別インスタンス） | 実装者/レビュアー分離は維持。実装完了→レビュー起動の直列運用 |
| 最重要ゲートの最終検証 | Fable 5（本体が直接実施） | 核心ロジックのみ。品質とトークン削減の両立 |
| デバッグ（kiro-debug、失敗時のみ） | Sonnet 5 | 必要時のみ起動 |

### 実測データ（根拠）

| 事象 | 実測値 |
|---|---|
| spec 生成サブエージェント 1本あたり | 約 195k〜233k tokens |
| Explore 調査（Haiku、広域探索） | 約 97k tokens / 44 tool uses |
| Explore 検証（Sonnet、反証志向の詳細検証） | 約 164k tokens / 65 tool uses |
| 3体並列時 | セッション上限到達（2回） |

## 3. sdd_base_template への反映箇所（実装ガイド）

### 3.1 スキルの並列ディスパッチ指示の書き換え
- **kiro-spec-batch/SKILL.md**: Step 3「wave 内の全 feature を並列サブエージェントで
  ディスパッチ（MUST be dispatched in parallel）」を、**同時実行数上限（デフォルト1）に
  従った逐次ディスパッチ**に変更。「Parallel within waves」の Critical Constraint を
  「Concurrency limit」に差し替え。wave の概念は依存順序の管理としては残してよい。
- **kiro-impl/SKILL.md**: 自律モード（タスク毎サブエージェント＋独立レビュー）が
  並列実行を指示している場合は同様に逐次化。実装→レビューの直列パイプは維持。
- **kiro-spec-requirements / kiro-spec-design / kiro-discovery**: 「parallel research via
  subagents」系の文言に同時実行数上限の但し書きを追加。

### 3.2 モデル割当の明記
- 各 SKILL.md のサブエージェント起動指示に、Agent ツールの `model` パラメータ指定を
  明記する（調査=haiku、実装/レビュー/spec生成=sonnet。オーケストレーターは指定なし=本体継承）。
- 将来のモデル名変更に備え、モデル名のハードコードは「tier 表現」
  （例: cheap-explore / standard-work / orchestrator）＋対応表1箇所への集約を推奨。

### 3.3 設定の外部化（推奨）
- 同時実行数上限とモデル tier 対応表を `.kiro/settings/agent-config.json`（新設）等で
  リポジトリ毎に上書き可能にする。利用プラン・上限はリポジトリ／契約により異なるため、
  テンプレートのデフォルトは「上限1・上記 tier 表」とし、余裕がある環境では並列数を
  引き上げられる構造にする。

### 3.4 中断復旧手順の追記
- 各スキルの Safety & Fallback 節に「Subagent が利用上限等で途中終了した場合:
  (1) ディスク上の成果物の完全性を検証（正常終端か）、(2) 完全なら不足メタデータ
  （spec.json 等）のみ本体が直接補完、(3) 不完全なら SendMessage で同一エージェントを
  再開（新規起動しない）」を追記。

### 3.5 エージェント整合（Codex 側）
- `.claude/skills/` と `.agents/skills/` は同一変更で揃える（既存ルール）。
- Codex 側にはモデル名 haiku/sonnet が存在しないため、`.agents/skills/` では
  tier 中立表現（「低コスト調査モデル」「標準作業モデル」）とし、Claude Code 固有の
  モデル名対応は `.claude/` 側の対応表にのみ置く。
- CLAUDE.md / AGENTS.md テンプレートに「エージェント構成ポリシー」節を追加し、
  上記の運用原則（同時2体・逐次・SendMessage 復旧・要約返却契約）を記載する。
