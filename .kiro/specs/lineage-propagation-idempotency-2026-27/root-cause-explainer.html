リザルトを取り込むたびに、
C2 が1行ずつ増えていった

系統連動（ME⇔MM）で付与されるカテゴリーが、同じリザルトを再取込するたびに重複して作られた。原因は単純で、重複防止のガードが「自分がこれから書く行」を絶対に見つけられない条件で検索していたことにある。日付の1日のずれが、そのまま行数の増加になった。

ひとことで言うと

ガードは apply_date <= レース当日 で「もう書いたか？」を探す。
しかしガードを通過して作られる行の apply_date は レース当日の翌日。
探す窓の外に自分で書き込んでいるので、何度取り込んでも毎回「まだ無い」と判定される。

01まず、所属をどう表現しているか

category_racers / apply_date・cancel_date・deleted

category_racers は「この選手はいつからいつまでこのカテゴリーだったか」を1行で表す台帳です。時点を持たない現在値のテーブルではなく、期間の履歴を積み上げていく構造になっています。

  • apply_date — その所属が発効する日（NOT NULL）
  • cancel_date — その所属が終わる日。NULL なら「今も継続中」
  • deleted — ソフト削除。「所属が終わった」ではなく「この行は最初から無かったことにする」という意味

ここは混同しやすいところです。cancel_date は業務上の事実（昇格して CM2 をやめた）を記録するのに対し、deleted は記録そのものの取り消し（誤登録だった、取込をやり直すので前回の書き込みを消す）です。履歴として残すなら cancel_date、無かったことにするなら deleted。両者は排他ではなく、有効な行を引くときは常に両方を見ます。

「ある日時点で有効な所属」の標準形

コード中に何度も現れる、この台帳への標準的な問い合わせはこの形です。

deleted = 0
AND apply_date <= $atDate                     ← その日までに発効している
AND (cancel_date IS NULL OR cancel_date >= $atDate)  ← その日にまだ終わっていない

実データで見ると、選手 MMJ-234-3001 のマスターズ側はこうなっています。

02「翌日から」という規約は、なぜ必要だったのか

2026-08-23 / commit c18d056

昇格すると、旧カテゴリーを終了して新カテゴリーを開始します。このとき旧の cancel_date と新の apply_date を同じ日にしてはいけない、という規約があります。理由は前節の標準形を見れば分かります。

基準日 D で検索したとき、条件は「apply_date <= D かつ cancel_date >= D」です。両端とも等号を含むので、旧行（cancel_date = D）も新行（apply_date = D）も両方とも条件を満たしてしまう。1人の選手が同じ系統で2つのカテゴリーを同時に持っているように見え、整合性検知が誤発火します。

そこで新カテゴリーは翌日から発効させます。昇格元系統側（ResultParamCalcComponent）は以前からこの規約でした。系統連動側（CategoryLineageLinker::propagateLinkedPromotion()）だけが、呼び出し元から渡された単一の日付を cancel_date と apply_date の両方にそのまま使っていたため、2026-08-23 に昇格元側へ揃える改訂が入りました。

// CategoryLineageLinker::propagateLinkedPromotion() — 2026-08-23 改訂で追加
$newApplyDate = date('Y/m/d', strtotime($atDate . ' +1 day'));
ここが分岐点

この改訂自体は正しい。同日衝突という実在の不具合を直しています。問題は、+1日 の計算を呼び出し元から Linker の内部へ移したとき、その日付を読みに行く側の一部に付け直さなかったことです。詳細は 07 で追います。

03同じ検索窓が、2つの別々の目的に使われている

grep -rn "apply_date <=" app | grep -v /Test/

ここが本件の核心です。apply_date <= $atDate という窓は、コード中で意味の違う2つの問いに使われています。

目的 A — 過去を問う

「レース当日、この選手は何を名乗っていたか」
過去の一時点の状態を再現する問い。この窓で正しい。未来日で登録された行（来季の先行付与、後から入った別大会の結果）を巻き込まないために、上限は必須。

目的 B — 自分の書き込みを問う

「この処理は、もう結果を書いていないか」
冪等性を守るための重複防止。この窓を使ってはいけない。問うべきは「自分が書いた行が在るか」であって、それが何日発効かは関係がない。

目的 B に日付の窓を使うと、書く日付を変えた瞬間にガードが効かなくなるという壊れ方をします。ガードの正しさが、無関係なはずの日付規約に依存してしまうからです。

初版の調査報告（research.md 1.2）との差分 — 3件とも採択済み

初版は「本体7箇所」として3箇所を修正対象に挙げていました。独立に数え直した結果を spec 側へ差し戻したところ、3件とも再検証のうえ採択され、修正対象は最終的に1箇所に絞られました。

  • 件数は7箇所ではなく12箇所。 初版の表は7件、脚注で3件（L366 / L668 / L796）に触れて計10件で、OrgUtilController の L297・L394 がどこにも現れませんでした。いずれも目的 A で正しいため結論は変わりませんが、用途で切り分けて修正対象を決める以上、母集団の正確さが設計の前提になります。
  • L1493（__setupCatRacerCancel）は「誤」ではなく A で正しい。 前回取込で cancel された旧行は cancel_date = レース当日 なので cancel_date >= $atDate に等号で該当し、取りこぼしません（実データ CM2 / id 94092 でも cancel_date は1回だけ）。spec 側の再検証でさらに強い根拠が出ました ——このメソッドの呼び出し6箇所の第2引数は、常に昇格元の下位カテゴリー（__rankUpMap[…]['needs']、array('CL2')、$oldCats[…]、array('C3','C4') 等）で、今回作成する連動先・昇格先を含みません。「前回作った行」はそもそもこのメソッドの対象外で、窓の有無とは無関係でした。
  • L1171 は「誤」で同意。ただし露呈条件は同日別大会。 冪等化削除が meet_code をキーに含むため、同一大会の再取込では前回行が先に消え、重複しません。露呈するのは同日開催の2大会目で、前回の昇格行（apply_date = 当日+1）が窓の外に落ちる場合です。同じ盲点は L1493 にも同じ形で存在します。

この「同日別大会」の盲点は、本件とは別系統の問題として spec のスコープ外と判断されました。昇格元側の +1日 規約は c18d056 の差分では変更されていないコンテキスト行であり、この盲点は今回の回帰より前から存在するためです。結果として修正対象は __findActiveCategoryRacerOnSide() の1箇所のみになりました。

取込5回ぶんの推移

同じ大会（もみじシクロクロス第2戦 / 2026-09-23）のリザルトが5回取り込まれました。ApiController::execAddResult() は再取込のたびに既存の racer_results を削除して作り直すため、リザルトidは毎回変わります。増えた5行が異なる racer_result_id を持っているのは、そのためです。

もう1人の選手で起きたこと

同じ大会の KNS-000-2879 も同様に5行できましたが、先頭4行は 2026-09-24 07:31〜07:32 に手動でソフト削除されています（deleted_date）。その約5分後、07:37:31 の5回目の取込でまた1行作られました（id 268616）。手で消しても、取り込み直せば復活する — ガードが日付窓に依存している限り、データ是正だけでは止まりません。是正はコード修正のデプロイ後に行う必要があります。

被害はこの2名だけではありません。現時点で有効な重複行を持つのは、ほかに CHB-178-0029(CM1) と TYM-190-0004(CM2) ＝ 大会 CXK-267-002 由来、KNS-167-0340(C2) と KNS-245-0133(C2) ＝ 大会 MMJ-267-001 由来の計4名です（いずれも2行ずつ）。

05なぜ昇格元側は1行で済んでいたのか

ResultParamCalcComponent::__execApplyRankUp() / __applyRankUp2CM()

同じ取込で、昇格元系統（CM1）は5回とも1行のままでした。こちら側は日付窓で「もう書いたか」を判定していないからです。判定する代わりに、書く前に同じ行を消しています。

// __execApplyRankUp() / __applyRankUp2CM() 共通のパターン
$applyDate = date('Y/m/d', strtotime($this->__atDate . ' +1 day'));

// 「同じ大会で同じ昇格をしているデータがあるなら削除する」
$conditions = array(
    'racer_code'    => $racerCode,
    'meet_code'     => $this->__meetCode,
    'category_code' => $categoryTo,
    'apply_date'    => $applyDate,      // ← 等値。自分が書くのと同じ値
    'reason_id'     => CategoryReason::$RESULT_UP->ID(),
);
// → 見つかった行を delete してから、あらためて create する

ポイントは apply_date を不等号ではなく等値で指定していることです。これから書く行と完全に同じキーで前回の行を探すので、日付規約を1日ずらしても両者は一緒に動き、ずれません。「探す条件」と「書く値」が同じ式から作られているのが、この側が壊れなかった理由です。

もう一点、削除条件に racer_result_id が含まれていないことも重要です。再取込のたびにリザルトidは変わるので、これを冪等キーに入れると前回の行が見つからなくなり、削除が空振りします。

この削除が実際に働いている様子は、2018年のデータにも残っています。CCM-189-9004 の C3 昇格行 id 25460 は deleted=1 で、その deleted_date（2018-11-28 01:16:30）が、作り直された id 25676 の created と秒まで一致します。再取込で前回行を消し、同じ内容を作り直した痕跡です。8年前から今日まで、昇格元側はこの方式で一貫して1行を保っています。

連動先側（propagateLinkedPromotion()）には、この削除がありません。あるのは日付窓のガードだけです。

06なぜエントリー補完は無傷なのか

supplementPairedCategoryOnEntryRegistration()

同じ CategoryLineageLinker の中に、似た処理がもう一つあります。エントリー登録時に対応ペアを補完する supplementPairedCategoryOnEntryRegistration() です。こちらは再実行しても増えません。理由は2つあり、どちらも「自分が書いた行を、自分で観測できる」という一点に帰着します。

  • 相手系統の保有確認に、上限のない別ヘルパーを使っている — __findCurrentlyActiveCategoryCodesOnSide() には apply_date <= 条件がなく、cancel_date だけで絞ります。未来日で付与済みの行も見えます。
  • 作る行の apply_date が大会当日そのまま — cancel を伴わないので +1日の回避が不要。書いた日付と探す範囲がずれません。

興味深いのは、このヘルパーが意図して分けられたという経緯です。docblock には、エントリー補完の $atDate は未来の大会開催日なので apply_date <= で絞ると未来日の既存行を見落として重複を作る、と明記されています（第3版・実装バグ修正）。まったく同じ形の不具合が、エントリー補完側では一度発見されて直されていたわけです。

一方で、エントリー元系統側の確認（__findCategoryCodesEffectiveAsOfDateOnSide(), L796）には apply_date <= があります。これは「大会当日に選手が実際に何を名乗っていたか」を問う目的 A なので、あって正しい。同じファイルの中で、目的ごとに窓の有無が正しく作り分けられている箇所です。

つまり

目的 A と目的 B を切り分ける設計判断は、このコードベースに既に存在していました。propagateLinkedPromotion() のガードだけが、その切り分けの適用から漏れています。

07混入の経緯 — 1つのコミットの中で読み手が分かれた

c18d056 / 2026-08-23 21:57 / PR#13 有識者レビュー第2ラウンド対応

この不具合は、最初からあったものではありません。2026-08-23 の改訂で新しく入りました。それ以前、連動先の書き込みは冪等でした。ただし「窓も書き込みも当日だったから」ではありません。実際はその逆で、窓も書き込みも当日+1日だったのです。

改訂前は、+1日の計算を呼び出し元が行っていました。ResultParamCalcComponent が既に手元に持っていた $applyDate（= 当日+1日）をそのまま Linker に渡し、Linker はその1つの値をガードの窓にも、旧行の cancel_date にも、新行の apply_date にも使っていました。1つの値が全経路を通るので、ガードは必ず自分の書き込みを観測できます。

// c18d056 の差分（ResultParamCalcComponent、2箇所とも）
- propagateLinkedPromotion($racerCode, $categoryTo, $result + ..., $applyDate);      // = 当日+1日
+ propagateLinkedPromotion($racerCode, $categoryTo, $result + ..., $this->__atDate); // = 当日

改訂は、この +1日 の計算を呼び出し元から Linker の内部へ移しました。呼び出し元は生のレース日を渡すだけでよくなり、規約への準拠は Linker が受け持つ ── 設計としては筋が通っています。問題は、内部で付け直した +1日 が新行の apply_date にだけ適用され、ガードの窓と cancel_date は渡された生の当日のままだったことです。

つまりガードは、それまで引数経由で +1日 をタダで受け取っていた。計算の置き場所が移ったとき、書き込み経路には明示的に付け直され、読み取り経路では静かに失われました。

コミットメッセージには lineageInspectionAtDate の新設と ResultParamCalcComponent の2箇所での設定が明記されています。「書く日付を変えたら、その日付を読む側も揃える」という作業は実際に行われていたのです。ただしその対象は整合性検知（CategoryRacer::afterSave()）に限られ、同じファイル内のガードには及びませんでした。

見落としが起きやすかった理由は、ガードが日付に依存していることが、ガード自身のコードから見えない点にあると考えます。検知側は $lineageInspectionAtDate という明示的な受け皿を持ち、そこに何を入れるかを考える必要があった。一方ガードは、呼び出し元が渡す $atDate をただ使うだけで、その値が「+1日 済みかどうか」に自分の正しさが懸かっていることをどこにも表明していません。propagateLinkedPromotion() の docblock は「+1日にする」理由を丁寧に説明していますが、「+1日にしたことで、当日以前しか見ないガードは自分の書き込みを観測できなくなる」とは書かれていません。

08まとめ

読み替えのポイント
  • apply_date <= $atDate は過去の一時点を再現するための窓であって、自分の書き込みの有無を確かめるための道具ではない。
  • 冪等性を守る側は、書く値と同じキーで探す（昇格元側の等値削除）か、そもそも日付で絞らない（エントリー補完側）かのどちらかを取るべきで、両者ともコードベースに実例がある。
  • 日付規約の変更は、その日付を読むすべての箇所の棚卸しを伴う。今回はそのうち検知側だけが更新された。
  • データ是正だけでは止まらない。取り込み直せば同じ行がまた作られる（KNS-000-2879 で実際に起きた）。
本件と切り離された、別系統の論点2つ

(1) 再取込で昇格そのものが取り消される場合の後始末。 順位や出走人数が訂正され、前回昇格した選手が今回は昇格しない場合、そのメソッド自体が呼ばれないため昇格行も連動行も残ります。本件とは独立した以前からある問題で、こちらでは検証していません。

(2) 同日別大会の盲点。 03 で触れた L1171 / L1493 の盲点は、spec 側で「+1日 規約は c18d056 より前から変わっておらず、原因系統が違う」として明確にスコープ外とされました。妥当な線引きだと思います。

(2) の根拠は当初「同一(選手・カテゴリー・apply_date)で meet_code が異なる有効な重複は全期間で1件のみ」という件数で書かれていましたが、meet_code の異同だけでは「同日開催の別大会」を判定できません。2デーレース（day1 と day2 で meet_code が違い、開催日も違う）やエントリーCSV由来の行が混ざるためです。実際 CCM-189-9004 / C3 / 2018-11-18 がこの形で拾われます —— Rapha Super Cross Nobeyama の day1 由来の昇格行と day2 のエントリー由来の行で、同日開催ではありません。

そこで判定を meets と結合し、開催日で突き合わせる形に差し替えました。

SELECT c.racer_code, c.category_code, c.apply_date,
       COUNT(DISTINCT c.meet_code) nmeet, COUNT(DISTINCT m.at_date) ndate
FROM category_racers c JOIN meets m ON m.code = c.meet_code
WHERE c.deleted=0 AND c.reason_id IN (2,12) AND c.cancel_date IS NULL
GROUP BY c.racer_code, c.category_code, c.apply_date
HAVING nmeet > 1 AND ndate = 1;

→ Empty set

昇格・連動由来で「同日開催の別大会」にまたがる有効な重複は、全期間で0件。 件数を数えるより強い形の根拠になりました。本欠陥由来の5選手8行は、いずれも nmeet = 1（同一大会の再取込）です。
