# 成果物の二層化ポリシー（一次=正本 / 二次=派生ビュー）

リポジトリ非依存のベースルール層として全リポジトリへ配布される。

> **一次成果物(md)が唯一の正本(Source of Truth)。二次成果物(PDF/Word/PPT 等)は一次から
> 一方向で再生成する派生ビューであり、手編集禁止・再生成可能なビルド成果物として扱う。**

## 1. 二層の定義

| 層 | 実体 | 権威 | 変換方向 | 承認・差分レビュー |
|---|---|---|---|---|
| 一次成果物 | `.kiro/specs/<id>/*.md`（requirements/design/tasks 等） | **正本（唯一の権威）** | — | **常に一次側で行う** |
| 二次成果物 | PDF / Word / PowerPoint（＋opt-in で Excel・作図） | 派生ビュー（再生成物） | 一次 → 二次の**一方向のみ** | 行わない（再生成で更新） |

- 二次成果物を**手編集しない**。修正は一次(md)を直し、再生成する。
- 二次 → 一次の**逆変換は提供しない**（正本を一意に保つため）。
- 正本 `design.md` は**物理分割しない**。監査対象別の人間向け文書は「二次生成（節スライス）」で満たす。

## 2. 出力先と管理

| 種別 | 出力先 | git |
|---|---|---|
| ビルド成果物（PDF/Word/PPT 等） | リポジトリ直下 `outputs/<spec-id>/` | `.gitignore` 対象（再生成可能） |
| PII を含む成果物 | `.kiro/specs/<id>/outputs/`（既存の隔離先） | `.gitignore` 対象 |

- 生成時は**出力先を明示するメッセージ**を出す。特に PII 隔離先へ出力した場合はその旨を明示する。
- 保管が必要な二次成果物は、別途アーカイブ（外部ストレージ、または意図的に明示コミット）する。

## 3. フォーマット × 成果物の現実ライン

| フォーマット | 基盤標準 | 手段 |
|---|---|---|
| Markdown（正本） | ✅ 正本 | — |
| Word (.docx) | ✅ 本命 | pandoc |
| PDF | ✅ 対応 | pandoc（docx/HTML 経由 or PDF エンジン） |
| PowerPoint (.pptx) | △ 限定 | pandoc md→pptx（テキスト・箇条書き・表・画像中心。図多用は弱い） |
| Excel (.xlsx) | 🔌 別pkg | pandoc 外（openpyxl/exceljs 等で md 表→xlsx） |
| 図（ER/クラス/シーケンス/構成） | 🔌 推奨opt-in | Mermaid → `mmdc` で SVG/PNG 化して埋込。厳密UMLは PlantUML |

**役割分担の指針**: 文章・図＝PDF/Word（＋PPT）。表主体で編集・進捗管理が要るもの（テーブル定義・
テストケース・タスク）＝Excel。図そのものは Excel に載せず「図＝PNG in Word/PDF」とする。

### フェーズ × 推奨フォーマット対応表
| フェーズ / 論理成果物 | 推奨フォーマット | 備考 |
|---|---|---|
| 要件定義（requirements） | Word / PDF（＋PPT 要約） | 文章中心 |
| 基本設計（アーキ・構成図） | Word / PDF | Mermaid 図は PNG 埋込 |
| 詳細設計: API 仕様 | Word / PDF | この機能固有の契約は design.md 節から生成 |
| 詳細設計: ER / クラス / シーケンス図 | PNG in Word/PDF | Mermaid→mmdc（厳密UMLは PlantUML・opt-in） |
| 詳細設計: テーブル定義一覧 | Excel（opt-in） | 表主体・編集需要あり |
| テストケース / タスク一覧 | Excel（opt-in） | 進捗管理需要あり |

> レンダラ（pandoc/mmdc/PDF エンジン/Excel 変換器）は**基盤に同梱しない**。必要な環境で opt-in 取得する
> （`install-renderers`）。未導入フォーマットは生成時に「未生成（要 install）」と明示し、他成果物の生成は継続する。

## 4. 層の整理（横断規約 ↔ 機能別）

肥大化と重複を避けるため、設計要素を置き場で振り分ける。

| 層 | 置き場 | 内容 | 例 |
|---|---|---|---|
| 横断規約（どう作るか） | `.kiro/steering/steering-custom/`（`api-standards`/`error-handling`/`security`/`authentication`/`database`/`testing` が受け皿） | プロジェクト全体に効くルール・標準。一度書けば全機能に効く | 「API はこの規約」「エラーはこの方式」「認証はこの標準」 |
| 機能別（この機能で何を作るか） | `.kiro/specs/<id>/design.md` の節（→二次で担当別ビュー生成） | この機能固有の設計 | 「この機能のエンドポイント一覧」「この機能の ER 図」 |

- **横断規約を各機能の `design.md` に重複記載しない（DRY）。** design.md は機能固有の設計に集中する。
- 例: "api-spec" は1つではなく「API 標準（steering）」と「この機能の API 契約（design.md 節）」に分かれる。

## 5. 生成の粒度

- **全文変換**: 正本 md 全体を単一の二次ファイルへ（節スライス指定が無い場合の既定フォールバック）。
- **節スライス**: 指定した見出し／アンカーに対応する節のみを抽出し、監査対象別の二次ファイルを生成する。
  指定した見出しが正本に存在しない場合はエラー報告し、空ファイルを生成しない。
- 希望する二次成果物は「論理成果物 → フォーマット」のマニフェスト（`deliverables.manifest`）で宣言できる。
  宣言が無ければ全文変換の既定フォーマット（Word、無ければ PDF）のみを生成する。
