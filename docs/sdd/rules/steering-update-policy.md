# 根本原因・再発防止策のsteering反映ポリシー

## 基本原則

1. **不具合の調査・修正作業（バグ改修）で根本原因と再発防止策が確定した時点で、
   `.kiro/steering/` へ反映することを義務とする。** 修正の完了・マージを待たず、
   「なぜ起きたか（機械的原因・プロセス欠陥）」「どう防ぐか（再発防止策）」が
   確定した時点で行う。
2. **spec固有の`agreement-log.md`・`research.md`への記録だけでは不十分。** それらは
   当該specの担当者以外が読む保証がなく、他spec・将来のタスクへの拘束力を持たない。
   `.kiro/steering/`はCLAUDE.mdで「全体をプロジェクトメモリとしてロードする」と明記
   されており、毎セッション必ず読み込まれる場所である点が本質的に異なる。
3. **既存の該当steeringファイルがあれば追記し、なければ`/kiro-steering-custom`スキル
   等で新規作成する。** 汎用的に再発しうる原因（外部情報源の誤読、特定のデータ構造の
   誤解、特定ライブラリ・フレームワークの落とし穴等）は、次に似た作業をする別セッション
   が自動的に教訓を得られる場所に置く。
4. **spec側の記録（agreement-log.md等）は経緯・決定の証跡として残し、削除・書き換えは
   しない。** steeringへの反映は「昇格」であって「移動」ではない——steeringには一般化
   した教訓・ルールを書き、spec側には固有の経緯（日付・具体的な数値・関係者）を残す。

## 判断基準（steeringに載せるべきか）

- **載せる**: 同種の作業（同じ外部情報源の参照、同じデータパターンの扱い、同じ
  ツール・ライブラリの利用）が将来の別specでも発生しうる場合
- **載せない**: そのspec・その大会・その選手固有の一回限りの事情（agreement-log.md
  に残せば十分）

迷う場合は、「次にこの種の作業をする別セッションが、このsteeringファイルを読まずに
同じ間違いを繰り返しうるか」で判断する。繰り返しうるなら載せる。

## 適用例

- season-rules-2026-27でのMM2→MM1昇格閾値誤読インシデント（2026-09-24）:
  外部ページのrowspan結合テーブルの誤読という、他specでも再発しうる原因だったため、
  `.kiro/steering/external-rule-source-verification.md`を新規作成して反映した。
