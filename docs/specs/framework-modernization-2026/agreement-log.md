### 背景・依頼

- 既存 `doc/update_plan/` を参考にしつつ **新規計画** を策定。

### ユーザー方針（質問への回答）
- ゴール水準は **水準2（サポート＋近代化）と水準3（全面刷新）を比較したい**。
- 水準3の場合は **乗り換え先の言語/FWの提案と根拠** を提示すること。
- cyclox2web は水準2(CakePHP5) / CI4 のほか、**乗り換え前提の計画と見積もりも欲しい**。
- cyclox2res-sys も同様の扱い。

### 調査で判明した重要事実
1. 実行PHPは既に **7.3**（既存計画の「PHP 5.x前提」は誤り）。ただし7.3もEOL。
2. **両アプリは同一DB `cyclox2` を共有**（res-sysは読み取り専用）。スキーマ不変が安全弁。
3. **自動テスト両アプリともゼロ** → 最大リスク。移行前のcharacterizationテスト整備が全シナリオ前提。
4. CakePHP 2 は他バージョンへの in-place 移行経路なし（実質再実装）。

### 決定・提案
- 比較シナリオを **S2 / S3a / S3b** で定義（README §3）。
- 水準3の移行先提案: **PHP継続 + Laravel 12**（根拠は README §4）。水準2の本命は CakePHP5 / CI4。
- 推奨着手順: 共通足場 → **res-sys 先行**（読み取り専用で低リスク）→ cyclox2web。最終水準確定前でも前半着手可能。
- res-sys には当座つなぎ策「CI3.1.13+PHP8.1（数日規模）」を選択肢として明記。

## 2026-06-25 ゴール水準の確定（S3b 採用・実装形態の再定義）

### 決定
- ゴール水準は **S3b（PHP 8.3 + Laravel 12）** を採用。
- ただし **res-sys は別サーバーで独立起動**するため、当初S3bの「単一コードベース統合（モノレポ）」は不採用。ユーザー判断: モノレポは使い勝手が悪い。
- 実装形態を **「共有ドメインパッケージ＋2デプロイ（ポリレポ維持）」** に再定義。

### 再定義の内容（README §4.1 に詳細）
- 共有DB `cyclox2` のモデル/集計ロジックを **共有 Composer パッケージ**に集約（二重実装の解消＝S3bの核心を実現）。
- アプリは2本のまま独立デプロイ: cyclox2web（管理サーバー・**スキーマ/マイグレーション所有**）／cyclox2res-sys（8081・別サーバー・**read-only接続**）。
- 配布は **GitHub を Composer VCS リポジトリ**として利用（現行 submodule 運用と親和、private Packagist/Satis 不要）。
- 共有パッケージはバージョニングし、両 consumer の CI でゴールデンテストを回す。

### 工数影響
- 旧S3b（単一統合）より軽量。cyclox2web は S3a+8〜12人日、res-sys は S3a+2〜4人日 程度の増分。
- 実装は段階的: まず S3a 相当（独立2 Laravel アプリ）→ 共有ロジックをパッケージ抽出して S3b 収束。
