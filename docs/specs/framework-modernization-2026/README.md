### 重要な構造的事実
1. **既存計画の前提（PHP 5.x）は誤り。実態は PHP 7.3。** リスク評価は既存計画よりやや軽い（PHP 8 化のギャップが小さい）。ただし PHP 7.3 も EOL であり「サポート切れ」状態は事実。
2. **両アプリは同一DB `cyclox2` を共有。** res-sys は cyclox2web が書いた成績を読むだけ。DB層で結合しているため、**DBスキーマは不変が大前提**（両者の同時破壊を避ける安全弁）。
3. **自動テストが両アプリともゼロ。** これが最大のリスク要因。安全圏の確保＝「移行前に振る舞いを固定する仕組み（characterization / golden-master テスト）」の整備が全シナリオの前提になる。
4. **cyclox2web は CakePHP 2 → 3/4/5 への in-place アップグレード経路が存在しない**（Cake2→3 は事実上書き換え）。したがって cyclox2web は「どの移行先でも再実装規模は大差なし」で、水準2でもコストは大きい。

## 3. シナリオ比較マトリクス

ゴール水準は合意済みの定義に従う:
- **水準2 = サポート＋近代化**: サポートされるPHP/FWへ載せ替え、加えてテスト基盤整備・コード品質改善・一部リファクタ。同系統FWを優先。
- **水準3 = 全面刷新**: FW・言語・アーキテクチャを最新へ刷新（必要なら言語/FW乗り換え・両アプリ統合）。

| シナリオ | cyclox2web 移行先 | res-sys 移行先 | ねらい | 相対リスク | 相対工数 |
|---|---|---|---|---|---|
| **S2: 水準2（同系統で延命＋近代化）** | CakePHP **5** + PHP 8.3 | CodeIgniter **4** + PHP 8.3 | サポート圏内＋テスト基盤。スタックは2系統のまま | 中 | 中 |
| **S3a: 水準3（乗り換え・別アプリのまま）** | **Laravel 12** + PHP 8.3 | **Laravel 12** + PHP 8.3 | スタック1本化・モダン化。アプリ境界は維持 | 中〜高 | 高 |
| **S3b: 水準3（論理統合・物理分離）★採用** | **Laravel 12**（共有ドメインパッケージを利用） | **Laravel 12**（同パッケージを利用・**別サーバーで独立デプロイ**） | 共有DBのモデル/集計ロジックを**共有Composerパッケージ**に集約して二重実装を解消。**デプロイは2本（ポリレポ維持・モノレポにしない）** | 中〜高 | 高 |

> **採用方針（2026-06-25 合意）**: S3b を採用。ただし res-sys は別サーバーで起動するため「単一コードベース統合」ではなく、**共有ドメイン層のみパッケージ化し、デプロイ可能なアプリは2本に分ける**形に再定義（[§4.1](#41-s3b-の実装形態共有パッケージ2デプロイ) 参照）。

> 補足: res-sys 単体には超低コストの **「CI 3.1.13 + PHP 8.1 で当座延命」** という選択肢もある（数日規模）。ただし CI3 は EOL のため恒久解にならない。「時間を買う」つなぎ策として水準2/3着手前のリスク低減に有効。詳細は res-sys 計画を参照。

## 4. 水準3の移行先提案と根拠

合意事項（水準3の場合は乗り換え先の提案と根拠を要求）に対する回答。

### 提案: **PHP 8.3 + Laravel 12**（言語は PHP を継続）

**言語は PHP を維持する根拠**
- 既存資産（DBスキーマ・業務ロジック・ドメイン知識）が PHP 前提で蓄積。言語を変える（例: Go/TS）と再実装コストとリスクが跳ね上がり「安全圏」と矛盾する。
- 運用基盤（Docker/Apache/MySQL）が PHP 前提で既に整備済み。
- ドメイン（シクロクロス大会運営）に既存 PHP ロジックの移植が最短。

**Laravel を推す根拠**
- PHP エコシステム最大。ライブラリ・採用市場・ドキュメント・**LLM学習データが最も豊富** → Claude Code 主体の開発と最も相性が良い（本計画の前提に直結）。
- Eloquent ORM が本システムの関係モデル（選手・大会・カテゴリ・ポイント・成績）に自然に対応。
- 長期サポート・セキュリティ更新が継続。テスト・キュー・スケジューラ（既存 cron/batch の受け皿）・認証が標準装備で、Cake の Acl/Console/Plugin 群の代替が揃う。

**代替案と不採用理由**
- *CakePHP 5*: Cake系知識を流用でき水準2の自然な延長。ただし2→5は結局再実装で、エコシステム規模は Laravel に劣る。**水準2の本命**として位置づけ、水準3では Laravel を推奨。
- *Symfony*: 堅牢だが学習コスト高・記述量多。小規模運用主体の本件にはオーバースペック。
- *CI4*: res-sys の自然な延長だが、cyclox2web の大規模ロジックには機能が薄く、結局カスタム実装が増える。

### 4.1 S3b の実装形態（共有パッケージ＋2デプロイ）

res-sys は別サーバーで起動するため、**モノレポ／単一デプロイは採らない**。S3b の狙い（共有DBに対するモデル/集計ロジックの二重実装の解消）を、デプロイ分離を保ったまま実現する。

#### コンポーネント構成（現行の2サブモジュール構造を踏襲）

| 要素 | 中身 | デプロイ |
|---|---|---|
| **共有ドメインパッケージ**（Composer） | 共有DB `cyclox2` の Eloquent モデル＋集計/クエリサービス（成績・ポイント・ランキング・カテゴリ） | デプロイ物ではない。両アプリが `composer require` で取り込む |
| **cyclox2web**（管理・Laravel） | 書き込み主体。**DBマイグレーションの所有者**。共有パッケージを利用 | 管理サーバー |
| **cyclox2res-sys**（閲覧・Laravel） | 読み取り専用（read-only DB接続）。共有パッケージの読みモデルで薄いビュー層 | **別サーバー（8081）で独立デプロイ** |

#### 設計上の決め事
- **スキーマ所有は cyclox2web 側に一本化**（書き込み側がマイグレーションを持つ）。res-sys はスキーマ非変更＝「DB不変が安全弁」を維持。
- res-sys は **read-only DBユーザー**で接続し、誤書き込みを構造的に防止。
- 共有パッケージは **GitHub を Composer VCS リポジトリとして配布**（現行 submodule 運用と親和。private Packagist / Satis 不要）。
- 共有パッケージは **バージョニング**し、各アプリ CI で「パッケージ更新 → 両 consumer のゴールデンテスト」を回す（片側破壊の検出）。

#### 得られること / トレードオフ
- ○ 二重実装の解消（S3b核心）／物理分離の維持（res-sys 独立サーバー）／公開境界・権限・リリース単位の分離／ポリレポのまま。
- △ 追加コスト: 共有パッケージ抽出・バージョニング・両 consumer CI。単一統合より軽く、**実質 S3a ＋共有パッケージ抽出（≒ S3a +α）**。

#### 段階アプローチ
まず S3a 相当（2つの独立 Laravel アプリ）を作り、共有ロジックを段階的に共有パッケージへ抽出して S3b へ収束させる。一括統合のリスクを避ける。

## 5. 工数モデル（全シナリオ共通の前提）

- 体制: **Claude Code（Opus）主体 ＋ 人間レビュア/テスター 1名（おおむね半稼働）**。
- Claude Code が担う: コード変換・移植・ボイラープレート生成・テストコード生成・差分修正。
- 人間が担う: 方針判断・レビュー承認・手動/結合テスト・本番切替判断。
- **律速はコード生成ではなく「レビュー＋テスト」**。自動テストがゼロのため、各シナリオは移行前のテスト基盤整備を工数に含む。
- 表記:
  - **従来換算工数**: 人手のみだった場合の目安（既存計画との比較用）。
  - **人間実working（人日）**: 本体制で人間が張り付く実日数。
  - **想定カレンダー**: 半稼働レビュー前提の概算所要期間。

数値はアプリ別計画の各表を参照。確度は ±40% のレンジ見積もり（テスト不在・未知の業務分岐により上振れしやすい）。

## 6. 全シナリオ共通の「安全圏」原則

1. **DBスキーマ不変**を絶対制約とする（両アプリ結合の保護）。変更が必要なら別計画として切り出す。
2. **旧環境を並行稼働**させ、移行先は別コンテナで構築 → 機能単位で切替 → 問題時は即ロールバック。
3. **移行前に characterization テスト（golden-master）** を整備し、特に計算系（成績集計・ポイント・昇格降格）は旧実装の出力をゴールデンとして固定。Claude Code でテスト生成を量産する。
4. **垂直スライス**（機能グループ単位）で移行・検証・切替を繰り返し、ビッグバン移行を避ける。
5. **記録**: 各フェーズの合意・判定根拠・テスト結果を本 `docs/specs/...` に常時更新（CLAUDE.md ルール9）。

## 7. 推奨ロードマップ（着手順）

採用方針（S3b）に基づく順序:

1. **共通フェーズ0（両アプリ共通の足場づくり）**
   - Docker に PHP 8.x ターゲットコンテナを追加（旧PHP 7.3 と並行）。
   - characterization テスト基盤を整備（HTTPレベルのゴールデン応答取得 ＋ 計算系の入出力固定）。
2. **res-sys を先行 Laravel 化**（規模小・読み取り専用 ＝ 失敗時の影響が限定的＝パイロット）。
   - つなぎが必要なら「CI 3.1.13 + PHP 8.1 延命」を先に当てて時間を確保。
   - res-sys で Laravel 移行パターン・テスト手法・read-only接続・コンテナ構成を確立。
3. **cyclox2web を Laravel 化**（規模大・書き込み主体・**スキーマ所有者**）。res-sys で確立したパターンを適用し計算系を重点検証。
4. **共有ドメインパッケージへ抽出（S3b 収束）**。両アプリで重複する共有DBモデル/集計ロジックを Composer パッケージへ切り出し、両 consumer が参照する形へ。GitHub を VCS リポジトリとして配布。
5. **両アプリを各サーバーへ独立デプロイ**（管理サーバー / 8081 公開サーバー）。Blue/Green ＋ ロールバック。

> 前半（足場・テスト・res-sys先行）は水準に依らず無駄にならない。S3b の核心である「共有パッケージ抽出」はステップ4でまとめて回収する（先に2アプリを成立させてから抽出する方が安全）。
