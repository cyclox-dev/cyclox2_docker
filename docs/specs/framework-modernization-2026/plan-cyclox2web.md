# cyclox2web 改修計画（CakePHP 2.10.24 → サポート圏）

> 親: [README.md](README.md) ／ 役割: 大会・選手・成績・ポイントの**運営管理アプリ（書き込み主体）**

---

## 1. 回収のゴール地点（水準別）

| 水準 | 移行先 | 明確なゴール（完了の定義） |
|---|---|---|
| **S2** | CakePHP **5** + PHP **8.3** | 全機能がCake5/PHP8.3で現行と同一の振る舞いで動作。DB不変・画面/業務ロジック等価。最低限のリグレッションテスト群が常設。旧Cake2環境を停止可能。 |
| **S3a** | **Laravel 12** + PHP **8.3**（別アプリ維持） | 同上に加え、Eloquentモデル化・認証/権限/バッチをLaravel標準へ。テスト・CI整備。スタックをLaravelに1本化。 |
| **S3b ★採用** | **Laravel 12**（共有ドメインパッケージを利用） | S3a＋共有DBのモデル/集計ロジックを**共有Composerパッケージ**へ抽出し二重実装を解消。**cyclox2web は本パッケージの主利用者かつDBマイグレーション所有者**。res-sys とは別デプロイ（ポリレポ維持）。 |

**採用**: S3b（PHP 8.3 + Laravel 12）。res-sys は別サーバー起動のため単一コードベース統合はせず、共有ドメイン層のみパッケージ化（[README §4.1](README.md#41-s3b-の実装形態共有パッケージ2デプロイ)）。

**全水準共通の不変条件**: DBスキーマ不変／既存業務ロジック（成績集計・ポイント・昇格降格）の出力等価／既存運用URL・API互換。

**S3b 固有の責務**: cyclox2web が **DBマイグレーション（スキーマ）を所有**し、共有パッケージのモデル/集計サービスを提供する側になる。res-sys は read-only でこれを利用する。

## 2. 影響範囲

### 機能領域（35コントローラ / 32モデル / 157ビュー）
- **選手管理** Racers, CategoryRacers, NameChangeLogs, UniteRacerLogs（名寄せ）
- **大会管理** Meets, MeetGroups, Seasons, EntryGroups, EntryCategories, EntryRacers
- **成績/記録** RacerResults, TimeRecords, TimeRecordInfos, RacesCategories, CategoryRaces
- **ポイント** PointSeries(Groups/Racers), MeetPointSeries, HoldPoints, RedLines（降格ライン）
- **カテゴリ** Categories, CategoryGroups（昇格・降格ロジック）
- **API** ApiController(1,685行) / ApiBaseController（エントリ・成績・選手データの外部連携）
- **運用ユーティリティ** OrgUtilController(1,268行), CSV入出力, 一時テーブル系（Tmp*）
- **計算エンジン** Component/ResultParamCalcComponent(2,193行), ResultReadComponent(627行)
- **バッチ** Console: ResultShell / CatLimitShell / OrgUtilShell / OneTimeShell（cron）
- **横断機能** Acl（認可）, Users（認証）, Search, Utils/SoftDelete（論理削除）, DebugKit, Maintenance

### 外部結合・運用面の影響
- **DB共有**: res-sys が同DBを読む → スキーマ・主要テーブルのデータ意味を変えないこと。
- **API互換**: 外部（計測・エントリ等）連携がある可能性 → エンドポイント/レスポンス形を維持。
- **cron/batch**: 成績再計算・ランキング更新・カテゴリ制限の定期実行 → 移行先のスケジューラへ等価移植。
- **インフラ**: Apache+mod_php / `.htaccess` / SSL / `database.php` マウント（docker-compose）→ コンテナ構成の更新。

## 3. リスク評価

| # | リスク | 影響 | 度合 | 対策（安全圏） |
|---|---|---|---|---|
| R1 | **自動テスト皆無**で振る舞い等価を保証できない | 高 | 高 | 移行前に characterization テスト（HTTPゴールデン＋計算系入出力固定）を必須整備 |
| R2 | **計算系ロジックの暗黙仕様**（成績集計/ポイント/昇格降格）の欠落・取りこぼし | 高 | 高 | ResultParamCalc/PointSeries/RedLine/CatLimit を最優先でゴールデン化し、本番相当データで突合 |
| R3 | **Cake2→他FWで直接移行経路なし**（実質再実装） | 高 | 中 | 機能単位の垂直スライス＋旧環境並行稼働で段階切替 |
| R4 | ORM/バリデーション/アソシエーションの差異による副作用 | 中 | 高 | モデル単位でゴールデン比較。SoftDelete挙動を明示移植 |
| R5 | **Acl/認証/権限**の移行漏れによる権限境界の崩れ | 高 | 中 | 権限マトリクスを表に起こし、移行先の認可で1:1再現してテスト |
| R6 | API/CSV/cron の互換崩れで外部連携・定期処理が停止 | 高 | 中 | 契約テスト（リクエスト/レスポンス・CSV列）を固定し回帰検出 |
| R7 | DBスキーマへの不用意な変更で res-sys 巻き添え | 高 | 低 | スキーマ不変を絶対制約。必要時は別計画で両アプリ同時対応 |
| R8 | 移植中の業務停止（運営シーズン中の事故） | 高 | 中 | オフシーズンに本切替。Blue/Green＋即時ロールバック |

## 4. 安全圏を前提とした作業・タスク計画

### フェーズ構成（水準共通の前半 → 水準依存の後半）

**P0. 足場（水準共通・無駄にならない投資）**
- PHP 8.x ターゲットコンテナを docker-compose に追加（旧 PHP7.3 と並行）。
- characterization テスト基盤: 主要画面のHTTPゴールデン応答取得、計算系の入出力スナップショット。
- 機能インベントリ＆権限マトリクスの作成（Acl/Users の棚卸し）。

**P1. 移行先の足場構築**
- S2: CakePHP 5 プロジェクト初期化、DB接続、認証/認可土台、AppController/AppModel等価層。
- S3: Laravel 12 初期化、Eloquent接続（既存スキーマへのモデルマッピング）、認証/認可（Policy/Gate）土台、スケジューラ/キュー設定。

**P2. 共通基盤・横断機能の移植**
- `Cyclox/`（Const/Util 4,100行）、共通ヘルパー、SoftDelete、Search 相当、レイアウト/テンプレート土台。

**P3. 機能グループ移行（垂直スライス・優先度順）**
1. 基本UI（index/view/edit/delete）＋レイアウト
2. 選手管理（名寄せ含む）
3. 大会・エントリ管理
4. カテゴリ管理（昇格降格）★計算系
5. ポイント管理（ランキング計算）★計算系
6. 成績/記録（ResultParamCalc）★計算系・最重要
7. API（外部連携・契約テスト固定）
8. バッチ/cron（スケジューラへ移植）
9. 運用ユーティリティ・CSV入出力

各スライスで: 移植 → ゴールデン突合 → レビュー承認 → 切替可否判定 を反復。

**P4. 結合・性能・セキュリティテスト → 本番切替（Blue/Green）→ 旧環境停止**

## 6. 推奨（採用方針 S3b に基づく）

- **cyclox2web は S3b の中核**: Laravel 12 化し、共有DBのモデル/集計ロジックを共有 Composer パッケージとして提供する側になる。**DBマイグレーション（スキーマ）の所有者**を cyclox2web に一本化する。
- 実装順は **段階的**に: まず S3a 相当（独立 Laravel アプリ）として成立させ、計算系をゴールデンで固めた後、共有ロジックをパッケージへ抽出して S3b へ収束（一括抽出のリスク回避）。
- **res-sys を先行**してパターン確立してから cyclox2web に着手するのが安全（[README §7](README.md)）。
- 計算系3群（成績/ポイント/カテゴリ昇格降格）は最重要リスク。本番相当データでの突合を必須にする。
